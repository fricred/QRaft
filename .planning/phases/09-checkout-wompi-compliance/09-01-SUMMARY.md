## Accomplishments

- Full orders + payments DDL written and committed (556 lines): 4 tables, 2 enum types, 1 sequence, 5 indexes, 4 functions, 2 triggers, 4 RLS policies, 3 GRANTs
- FSM trigger `validate_order_transition` enforces all 11-state order lifecycle transitions at the DB level — no app code can produce an invalid order state
- `create_order` RPC atomically inserts orders + order_items + payments in one plpgsql transaction with idempotency via `unique_violation` catch
- `payment_events.event_id TEXT PRIMARY KEY` provides Wompi webhook replay safety without any advisory locks
- All monetary amounts stored as whole COP pesos (INT); ×100 centavo conversion deferred to create_payment_intent Edge Function (Plan 02)

## Files Created/Modified

## Decisions Made

- `order_number` uses empty string `''` as the INSERT placeholder so the `WHEN (NEW.order_number IS NULL OR NEW.order_number = '')` trigger condition fires reliably regardless of default
- `IF NOT EXISTS` guards on `CREATE TYPE` blocks allow safe re-run of migration (idempotent DDL)
- `payment_events.payment_id` uses `ON DELETE SET NULL` to preserve audit log even if a payment row is administratively deleted
- `validate_order_transition` checks terminal states first (cancelled/refunded → always raise) before checking each originating state — single-exit-point FSM logic
- `apply_payment_event` maps all non-APPROVED Wompi statuses (DECLINED, VOIDED, ERROR) to `payment_failed` order status — retryable path via `payment_pending` reset in the FSM

## Threat Flags

| Flag | File | Mitigation |
|------|------|------------|
| T-09-01: Direct UPDATE from client | migration | RLS: no UPDATE policy on orders for authenticated role |
