  <action>
Create `supabase/migrations/20260505000000_orders_payments_schema.sql` containing the
following in order. All amounts are WHOLE COP PESOS (INT), never floats. Wompi multiply-by-100
conversion (pesos → centavos) happens in the create_payment_intent Edge Function (Plan 02).

1. ENUM types:
   - `order_status` with values:
     payment_pending, payment_failed, paid, received_by_ops, engraving,
     engraving_failed, engraving_done, shipped, delivered, cancelled, refunded
   - `payment_status` with values:
     pending, approved, declined, voided, error, refunded

2. TABLE `orders`:
   id UUID PK, order_number TEXT UNIQUE NOT NULL (pattern 'QRA-YYYY-NNNNNN' — generated
   by trigger using TO_CHAR + LPAD), user_id UUID REFERENCES auth.users ON DELETE RESTRICT,
   status order_status NOT NULL DEFAULT 'payment_pending',
   subtotal_cop INT NOT NULL, tax_cop INT NOT NULL, shipping_cop INT NOT NULL,
   total_cop INT NOT NULL,
   shipping_recipient_name TEXT NOT NULL, shipping_phone TEXT NOT NULL,
   shipping_department TEXT NOT NULL, shipping_city TEXT NOT NULL,
   shipping_address TEXT NOT NULL, shipping_notes TEXT,
   created_at TIMESTAMPTZ DEFAULT NOW(), paid_at TIMESTAMPTZ,
   received_at TIMESTAMPTZ, engraving_started_at TIMESTAMPTZ,
   engraving_done_at TIMESTAMPTZ, shipped_at TIMESTAMPTZ,
   delivered_at TIMESTAMPTZ, cancelled_at TIMESTAMPTZ.
   Indexes: idx_orders_user_status ON (user_id, status);
   idx_orders_ops_queue ON (status, created_at) WHERE status IN
   ('paid','received_by_ops','engraving','engraving_done').

3. TABLE `order_items`:
   id UUID PK, order_id UUID REFERENCES orders ON DELETE CASCADE,
   product_variant_id UUID REFERENCES product_variants ON DELETE RESTRICT,
   qr_code_id UUID REFERENCES qr_codes ON DELETE SET NULL,
   customization_snapshot JSONB NOT NULL,
   qr_png_url TEXT NOT NULL,
   unit_price_cop INT NOT NULL,
   quantity INT NOT NULL CHECK (quantity > 0),
   line_total_cop INT NOT NULL.

4. TABLE `payments`:
   id UUID PK, order_id UUID REFERENCES orders ON DELETE CASCADE,
   transaction_ref TEXT UNIQUE NOT NULL (the idempotency key we send to Wompi),
   wompi_transaction_id TEXT (nullable until first webhook),
   amount_cop INT NOT NULL,
   status payment_status NOT NULL DEFAULT 'pending',
   payment_method TEXT,
   raw_payload JSONB,
   created_at TIMESTAMPTZ DEFAULT NOW(), updated_at TIMESTAMPTZ DEFAULT NOW().

5. TABLE `payment_events` (idempotency log):
   event_id TEXT PRIMARY KEY, (Wompi's event id — PRIMARY KEY = UNIQUE enforced by PK)
   payment_id UUID REFERENCES payments,
   kind TEXT NOT NULL,
   payload JSONB NOT NULL,
   received_at TIMESTAMPTZ DEFAULT NOW().

6. FSM TRIGGER `validate_order_transition`:
   Fires BEFORE UPDATE OF status ON orders. Raises EXCEPTION for any invalid
   transition. Valid transitions (only these are allowed; all others raise):
   - payment_pending → payment_failed, paid, cancelled
   - payment_failed → payment_pending (retry), cancelled
   - paid → received_by_ops, cancelled, refunded
   - received_by_ops → engraving, cancelled, refunded
   - engraving → engraving_failed, engraving_done
   - engraving_failed → received_by_ops
   - engraving_done → shipped
   - shipped → delivered
   - delivered → refunded (admin only)
   - cancelled, refunded → (terminal — raise exception on any change)

7. FUNCTION `generate_order_number()` called by BEFORE INSERT trigger:
   Generates 'QRA-' || TO_CHAR(NOW(), 'YYYY') || '-' || LPAD(nextval('order_seq')::TEXT, 6, '0').
   Create SEQUENCE `order_seq` before the function.

8. FUNCTION `create_order(p_user_id UUID, p_cart_item_ids UUID[],
   p_shipping JSONB, p_idempotency_key TEXT) RETURNS UUID` (SECURITY DEFINER):
   - BEGIN
   - SELECT subtotal_cop, tax_cop, shipping_cop, total_cop FROM
     server_compute_order_totals(p_user_id) — reuse Phase 8 RPC
   - INSERT INTO orders (...) returning id INTO v_order_id
   - For each cart item id in p_cart_item_ids:
     INSERT INTO order_items (order_id, product_variant_id, qr_code_id,
     customization_snapshot, qr_png_url, unit_price_cop, quantity, line_total_cop)
     SELECT from cart_items JOIN product_variants
   - INSERT INTO payments (order_id, transaction_ref, amount_cop, status)
     VALUES (v_order_id, p_idempotency_key, total_cop, 'pending')
   - RETURN v_order_id
   - EXCEPTION when unique_violation RAISE 'order already created for this idempotency key'
   - END

9. FUNCTION `apply_payment_event(p_transaction_ref TEXT, p_wompi_status TEXT,
   p_wompi_transaction_id TEXT, p_payment_method TEXT, p_raw_payload JSONB)
   RETURNS VOID` (SECURITY DEFINER):
   - Update payments WHERE transaction_ref = p_transaction_ref:
     status = CASE p_wompi_status
       WHEN 'APPROVED' THEN 'approved'::payment_status
       WHEN 'DECLINED' THEN 'declined'::payment_status
       WHEN 'VOIDED'   THEN 'voided'::payment_status
       ELSE 'error'::payment_status
     END,
     wompi_transaction_id = p_wompi_transaction_id,
     payment_method = p_payment_method,
     raw_payload = p_raw_payload,
     updated_at = NOW()
   - Update orders.status and timestamp:
     IF approved → set status = 'paid', paid_at = NOW()
     IF declined/voided/error → set status = 'payment_failed'
     Use UPDATE orders SET ... WHERE id = (SELECT order_id FROM payments WHERE
     transaction_ref = p_transaction_ref)
     (The validate_order_transition trigger enforces FSM — no need to double-check here)

10. RLS POLICIES:
    - orders: SELECT own (user_id = auth.uid()); NO direct UPDATE/INSERT/DELETE
      from client (client uses create_order RPC only).
    - order_items: SELECT own via orders join; NO direct mutations.
    - payments: SELECT own via orders join; NO direct mutations.
    - payment_events: NO client access at all.
    For service-role reads (operator dashboard): policies rely on service_role
    bypassing RLS automatically — no separate policy needed.

11. GRANT EXECUTE on create_order and apply_payment_event to authenticated role.
    apply_payment_event also granted to service_role (for Edge Function using
    service_role key).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter client → Supabase RLS | Client sends authenticated JWT; RLS enforces user_id = auth.uid() on all reads |
| Edge Function → Postgres RPCs | Edge Function uses service_role key; RPCs are SECURITY DEFINER with explicit WHERE guards |
| Wompi → Edge Function webhook | Verified by SHA256 X-Event-Checksum in Plan 04; migration sets up the target tables |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Tampering | orders.status direct UPDATE from client | mitigate | RLS denies UPDATE on orders from authenticated role; only RPCs (SECURITY DEFINER) may mutate status |
| T-09-02 | Elevation of Privilege | create_order RPC spoofing another user's cart | mitigate | create_order is SECURITY DEFINER; uses p_user_id from auth.uid() cross-checked via WHERE user_id = p_user_id on cart_items |
| T-09-03 | Repudiation | No audit trail for status changes | mitigate | validate_order_transition trigger logs old/new status; paid_at/shipped_at timestamps immutable |
| T-09-04 | Information Disclosure | payment_events readable by client | mitigate | RLS: zero client access on payment_events table |
| T-09-05 | Denial of Service | Malformed p_cart_item_ids causing partial inserts | mitigate | create_order wrapped in single plpgsql transaction; any failure rolls back atomically |
</threat_model>
